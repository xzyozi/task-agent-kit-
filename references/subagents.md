# 親子 agent の共通契約

親 agent（オーケストレーター）が依頼を分類・分解し、専門 subagent に委譲し、結果を検証・統合するための、ツール非依存の規則。ツール固有の配置先・キー・権限は `references/agents/` のツール別の文書に書く。この文書には書かない。

親 agent と subagent の本文は、`references/agent-anatomy.md` の本文構造に従う。雛形は `templates/orchestrator.md` と `templates/subagent.md`。

## 責務の分担

| 担当     | 責務                                                                     | 持たない責務                           |
| -------- | ------------------------------------------------------------------------ | -------------------------------------- |
| 親 agent | 要件確認、分類、分解、委譲、結果の検証、統合、承認の取得、利用者への報告 | 専門作業そのもの（調査・実装・検証）   |
| subagent | 割り当てられた1つの専門作業の実行、結果の報告                            | 分類、他の subagent の選択、承認の取得 |

利用者への質問と、承認が必要な操作の承認取得は、親だけが行う。subagent は、承認が必要な操作に当たった時点で停止し、親へ返す。

## 固定する規則

1. **委譲は1階層**: 親から子への委譲だけを許す。子から孫への再委譲は禁止する。子が別の専門作業を必要とした場合は、実行せず「差し戻し」で親へ返す。
2. **既定は逐次実行**: 委譲は1件ずつ行い、結果を検証してから次へ進む。
3. **並列は例外**: 次をすべて満たす場合だけ、親が明示して並列にしてよい。
   - すべての子が読み取り専用である、または書き込み対象が互いに重ならない。
   - 子の結果が互いに依存しない。
4. **書き込みの競合を避ける**: 同じファイルに書き込む子は、同時に動かさない。親が委譲時に、子ごとの書き込み対象を明示する。
5. **権限は親以下**: 子の権限は、親の権限を超えない。読み取りだけで足りる子には、書き込みと実行を与えない。
6. **subagent の一覧は固定**: 親が委譲できるのは、`PROJECT.md` の「Canonical locations」に記録された subagent だけ。一覧にない agent へ委譲しない。
7. **書き込みは二重に確認する**: 子に書き込みを許すのは、委譲依頼で書き込み対象が明示され、かつ登録簿でその子が書き込み可と記載されている場合だけ。両者が食い違う場合は、狭いほうを採用して書き込みを拒否し、拒否したことを報告する。
8. **親は専門作業を行わない**: 小さな作業でも、親が直接行わない。subagent へ委譲するか、利用者へ戻す。
9. **承認は親だけが取る**: 親は対話型を既定とする。自律実行型にしてよいのは子だけで、承認が必要な操作に当たった子は停止して親へ返す。

## 登録簿

`PROJECT.md` の「Canonical locations」に、subagent ごとに次の項目を表で記録する。

| 項目             | 内容                                       |
| ---------------- | ------------------------------------------ |
| 名前             | subagent の名前                            |
| 受け付ける依頼   | この子が扱う依頼                           |
| 受け付けない依頼 | この子が扱わない依頼。差し戻しの基準になる |
| 許可ツール       | 子が使えるツール。親の権限を超えない       |
| 書き込み可否     | 可または不可。可の場合は書き込み可能な対象 |

## 親の流れ

次の順に進める。

1. **分類**: 依頼を、登録された subagent の受け付ける依頼に照らして分類する。どれにも当たらない、または複数に等しく当たる場合は、推測せず利用者に確認する。
2. **分解**: 依頼を、1つの subagent が1回で完了できる単位に分ける。単位ごとに完了条件を決める。
3. **委譲**: 次の「委譲依頼」を渡して、1件ずつ委譲する。
4. **検証**: 子の「結果報告」を、完了条件と照らして確認する。確認は、根拠、変更対象の範囲、検証結果の3点に限る。子の作業全体を再実行しない。
5. **統合**: 検証を通った結果だけを統合する。未解決事項は、統合結果から消さずに残す。
6. **報告**: 完了した部分、未解決の部分、次に必要な判断を、利用者に報告する。

## 委譲依頼（親から子へ渡す項目）

| 項目           | 内容                                                       |
| -------------- | ---------------------------------------------------------- |
| 目的           | 子が達成する1つの目的                                      |
| 対象範囲       | 扱ってよい対象と、扱わない対象                             |
| 入力と前提     | 子が使う入力、すでに確定している事項                       |
| 許可された操作 | 読み取り・書き込み・実行のうち、許可するものと書き込み対象 |
| 停止条件       | 子が止まって親へ返す条件                                   |
| 完了条件       | 子が達成を自分で確認できる条件                             |
| 報告形式       | 次の「結果報告」の項目                                     |

子は、委譲依頼に書かれていない前提を推測で補わない。不足は「不足情報」として返す。

## 結果報告（子から親へ返す項目）

| 項目           | 内容                                                             |
| -------------- | ---------------------------------------------------------------- |
| 状態           | 次の5つのいずれか                                                |
| 実施内容       | 実際に行った操作                                                 |
| 根拠           | 結論を支える確認結果。確認していないことを確認済みとして書かない |
| 変更対象       | 変更したファイルや対象。変更がなければ「なし」                   |
| 検証結果       | 完了条件に対する確認結果。確認できなかった項目は、その旨を書く   |
| 未解決事項     | 残った問題、不足情報                                             |
| 次に必要な判断 | 親または利用者が決める事項                                       |

### 状態の定義

| 状態           | 意味                                 | 親の扱い                                               |
| -------------- | ------------------------------------ | ------------------------------------------------------ |
| `completed`    | 完了条件をすべて満たした             | 検証して受理する                                       |
| `partial`      | 完了条件の一部だけ満たした           | 満たした部分だけ受理する。未達は未解決にする           |
| `failed`       | 実行したが、完了条件を満たせなかった | 原因を確認する。再試行は1回まで                        |
| `blocked`      | 承認、権限、情報の不足で進めない     | 親が解消できる場合だけ解消し、できなければ利用者へ返す |
| `out_of_scope` | 割り当てられた専門作業の範囲外だった | 別の subagent への委譲を、親が改めて判断する           |

## 部分成功と失敗の扱い

- 親は、完了条件を満たした部分だけを受理する。満たしていない部分は「未解決」として必ず報告し、完了とは報告しない。
- `failed` の子は、原因を確認したうえで、再試行を1回までに限る。同じ失敗が繰り返された場合は、親も停止して、利用者へ報告する。`references/safety-baseline.md` の停止条件に従う。
- 子が `blocked` または `out_of_scope` を返した場合、親は推測で埋めて続行しない。

## 親が停止して利用者へ返す条件

次のいずれかに当たる場合、親は作業を止めて報告する。

- 依頼を分類できない、または委譲先が一意に決まらない。
- 委譲先の subagent が一覧に存在しない、または権限が親を超えている。
- 子が承認の必要な操作を要求した。
- 書き込み対象の競合が解消できない。
- 同じ失敗が2回続いた。
- 子の報告に、根拠のない完了、または範囲外の変更がある。

## 書かないこと

- 特定のツール名、キー、`capability` 名、配置先。これらは `references/agents/` に書く。
- 特定の業務ドメインのサーバ、パス、コマンド。
- 安全規約の複製。共通の安全規約は `references/safety-baseline.md` を参照する。
